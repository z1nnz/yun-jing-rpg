> 2026-10-29，Claude Code 撰寫。z1nnz：「你自己也學習一下怎麼查看、怎麼檢查協作者的 PR」；同時要教 Codex 照同一套方法審。

## 1. 審查的目的

PR 審查不是挑毛病，而是回答三個問題：
1. **它做的是工作包要的東西嗎？**（範圍）
2. **它放得進我們現在的世界嗎？**（世界觀、地圖、比例、風格、玩法、伺服器）
3. **它進得了手機網頁嗎？**（效能、檔案大小、技術規格）

三個都是「是」才合併。只差一點的，寫清楚要改什麼，**每一條都要能照著做**。

## 2. 怎麼看（工具）

這台電腦沒有 `gh`，用 GitHub REST API 加 git 存的憑證。腳本在 `tools/github/`（只讀，不會改 GitHub 上的任何東西；不會印出憑證）：

```bash
# 1. 列出 PR：作者、分支、檔案數、審查狀態
node tools/github/list-prs.mjs open
# 2. 單一 PR：說明、檔案依資料夾／副檔名分組、有沒有碰到共用路徑、CI、留言
node tools/github/pr-detail.mjs 45
# 3. 抓下分支，不切換工作樹，直接讀檔
git fetch origin <分支>
git ls-tree -r --name-only FETCH_HEAD <資料夾>
git show FETCH_HEAD:<檔案路徑>
```

- 讀數字（面數、尺寸、貼圖大小）時，讀交件附的 `*_model_info.json`，不要只看 PR 說明。
- 要實際看模型或跑玩法時，另開工作樹：`git worktree add D:\yun-jing-rpg-workspace\yun-jing-rpg-review-<PR號> FETCH_HEAD`，看完再刪掉。不要在主場景工作樹切分支。

## 3. 審查清單（照順序）

### A. 範圍與安全

- [ ] PR 說明照範本寫：目的、輸入、輸出、邊界、完成條件、目前狀態。
- [ ] **只改自己的資料夾**：用 `pr-detail.mjs` 的「touches shared/core paths」那段檢查。
  - 碰到 `apps/game/Assets/YunJing`、`ProjectSettings`、`Packages`、`services`、`packages` 的，要特別問為什麼。
- [ ] 大檔走 Git LFS：模型、貼圖、影片在 diff 裡應該是 `+3/-0` 的指標檔。
- [ ] 沒有 Unity `Library/`、暫存檔、個人設定。
- [ ] 分支落後 main 多少：`mergeable_state: behind` 時請作者先合併 main。

### B. 放得進現在的世界嗎（最重要）

對照：
- [世界觀總綱](../story/world-lore-v1.md)
- [區塊規劃](../execution/novice-world-block-plan.md)
- [遊戲整體架構](../game-structure-v1.md)

- [ ] **位置**：這件東西放在哪個區塊、哪個格位？
  - 區塊規劃裡沒有它的位置，就要先定位置（加格位或區塊）才能合併；
  - 不能「先做了再找地方放」。
- [ ] **空間**：它屬於領地、大世界還是秘境（規範 §2.1）？
  - 例如種植、練功放在大世界就錯了。
- [ ] **尺寸**：和地圖資料對得上嗎？例如河道寬度和 `novice-village.json` 的溪流寬度、門寬和 1.75 m 角色。
- [ ] **世界觀**：
  - 名字和文字照用語表、取名三層法；
  - 不說破未來（規範 §3）；
  - 東西對應世界觀的哪一層？
- [ ] **風格**：符合世界常數與該區域的配色（建模規格 §11）；和相鄰區域、其他協作者的同類件並排看得出是同一個世界。

### C. 技術規格

- [ ] **面數**：記下每件的面數，對照建模規格 §6 的參考值。**不要求減面**，只要求有 LOD1／LOD2。
- [ ] **大量重複的件**（河段、路段、牆）要算總量：一段 100 m 的河要放幾件？乘起來多少面？
  - 分清楚**下載大小**（同一個檔案重複用，只下載一次）和**畫面負擔**（同時畫出多少面，靠 LOD 和遮擋處理）。
  - 品質好但面數高的，先要求補 LOD，接進遊戲**實測**；不夠快時，只調整遠處用的簡化版，近景的 LOD0 不動。
- [ ] LOD1／LOD2 有沒有，比例對不對（50%、15%）。
- [ ] 小於 2 cm 的起伏放法線貼圖，不建成幾何（建模規格 §5）。
- [ ] 原點在腳印中心、底部高度 0；接口和碰撞照接地規格。
- [ ] 檔名有版本號，不覆蓋舊版；物件名照 `SM_<套件>_<名稱>_LOD0`。
- [ ] 回匯驗證：GLB／FBX 回匯後面數一致。

### C2. 品質（z1nnz 2026-10-30：「我不想要品質下降」）

- [ ] **品質優先於面數**：面數上限只是參考。品質好、面數高的，用 LOD 和手機實測解決，不要求減 LOD0。
- [ ] **新版和舊版並排比較**：同一件的新舊渲染圖放在一起看。新版面數大幅下降時要特別小心，外觀退步就退回。
  - 例：#52 比 #51 面數降了約 75%，石頭變得像軟墊、銅件變成平的橘色條，所以退回。
- [ ] 和三視圖比：形體、切面、材質細節有沒有做出來。

### D. 玩法與伺服器

- [ ] 玩家能做的事，有沒有寫成伺服器動作？
  - 只在本機展示、結果沒有存到伺服器的，**不算完成**，只算「展示」；
  - 要列出接進遊戲需要的伺服器動作（名稱、輸入、結果、冷卻、重送不重複）。
- [ ] 有測試，而且測試真的會失敗（不是永遠通過）。
- [ ] 手機可以操作（觸控、橫向）。

### E. 驗證證據

- [ ] 四視圖加人形尺、遊戲內截圖、並排比較（建模規格 §8）。
- [ ] 截圖是**真的跑出來的**，不是概念圖。
- [ ] 作者自己列的「未完成」是否誠實：和我們實際看到的一致嗎？

## 4. 回饋怎麼寫

- **先講結論**：可以合併／改完可以合併／要大改。
- **每條回饋包含**：
  - 哪個檔案或哪件；
  - 問題是什麼（附數字）；
  - 要改成什麼（附標準出處）；
  - 為什麼。
- **好的地方也要寫**，讓作者知道哪些要保持。
- **分「必改」和「建議」**：必改的沒改不合併；建議的可以下一輪。
- 回饋寫在 PR 留言或審查文件（`docs/execution/reviews/PR<號>-<日期>.md`）。
  - 要貼到 GitHub 上，先給 z1nnz 看，由 z1nnz 決定。
